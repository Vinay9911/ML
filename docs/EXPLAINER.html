Event Digital Twin — how it all works

A plain-language guide to the project: what it is, how the pieces fit together, what each finished model does, and how to run any of them.

Covers the 10 models built so far of 25. This file is updated as each new model lands — if it disagrees with PROGRESS.md, PROGRESS.md is right.

Want to see them actually run? Start the services with uv run python scripts/serve_all.py and open docs/SIMULATION.html — a live map where you can run any model, browse the real data going in, and see the real output coming out. This page explains how it all works; that one shows it.

1. What this project is

Imagine a control room for a massive religious gathering — Kumbh Mela scale, tens of millions of people over a month, riverside bathing ghats, a temporary city built for the occasion. On the wall is a live dashboard showing what is happening right now and what is about to happen.

This repository is not that dashboard. It is the brain behind it: 25 small, independent services, each answering exactly one operational question, each returning its answer in the same JSON shape so the dashboard team writes one parser for all 25.

The three things that define the project

No real data yet Everything runs on a synthetic world we generate — 31 days, 8 zones, 4 gates, roughly 280,000 rows per scenario — plus a few genuinely real public sources. Every row and every response carries is_synthetic so nobody can mistake one for the other.
One fixed contract Every service returns the identical JSON structure and exposes the same four endpoints. A model that cannot answer still answers — it says status: degraded and explains why.
Swappable for real data Each table can be replaced by a real feed later without touching model code. You change data_source: synthetic to replay in a config file.

The demo story

It is 06:00 on the peak bathing day. Crowd is building at Ghat A. The system warns that density will cross the danger line in about 45 minutes — early enough to act. Every model in the project is pointed at that same moment in time (demo_now = 2027-08-02T06:00:00+05:30), so their answers line up.

2. The big picture

Data flows in one direction. Real public sources and a synthetic generator build a world; the shared library reads it; the models read the library and each other's outputs.

REAL SOURCES SYNTHETIC GENERATOR ┌──────────────────────┐ ┌──────────────────────────┐ │ Open-Meteo weather │ │ crowd flow · gates │ │ Open-Meteo air qual. │ ──────▶ │ parking · transit · water│ │ OpenStreetMap roads │ │ power · waste · food ... │ │ AI4I machine dataset │ │ 31 days x 8 zones │ └──────────────────────┘ └────────────┬─────────────┘ (cached to disk, │ 28 tables, ~280k rows works offline) │ per scenario ▼ ┌────────────────────────────────────┐ │ 00_common / twin_common │ │ contracts · config · engines │ │ IO · upstream resolution · API │ └────────────────┬───────────────────┘ │ ┌────────────────┬───────────────┼───────────────┬────────────────┐ ▼ ▼ ▼ ▼ ▼ M21 → M01 → M05 → M06 → ... M25 weather footfall parking shuttles (no upstream) (13 models (M06 reads (M25 reads read this) both M01+M05) 11 models)
Models never import each other. A model reads another model's JSON output, resolved in a fixed order: inline in the request → a URL in an environment variable → a saved sample file → a stub. That means any one service runs completely alone, and the response always says which source it actually used.

The operating loop

Observe ──▶ Predict ──▶ Simulate ──▶ Optimize ──▶ Act ──▶ Learn (sensors) (M01, M05..) (M11 evac) (M16, M24) (human) (feedback) ▲ every recommendation ────┘ carries requires_approval: true

That last point is deliberate and non-negotiable in the contract: no model can propose an action that executes itself. A human always approves.

3. Where the data comes from

The synthetic world

One command builds an entire month of the event:

uv run python -m twin_common.synthetic.generate --scenario S01

It produces 28 tables (D01–D25) — footfall, gate entries, parking, transit, water, power, waste, food, network, air quality, asset telemetry and more — then runs about 130 internal consistency checks and refuses to write if any fail.

Common random numbers. Every scenario draws the same random noise, so the only difference between two worlds is the intervention itself. Without this, comparing "30 % more crowd" against the baseline was confounded by several percent of noise — a small effect could come out backwards. Now S02 is exactly 1.3000× S01.

The real sources

SourceUsed forLicence

All four cache to disk on first use. Set TWIN_OFFLINE=1 and nothing touches the network — services degrade and say so rather than failing.

4. What every model returns

This is the single most important thing to understand, because all 25 models return exactly this shape. Here is a real response from M01, trimmed:

{
  "model_id": "M01",
  "as_of": "2027-08-02T06:00:00+05:30",   // the moment being answered for
  "scenario_id": "S01",                    // which what-if (S01 = normal)
  "data_source": "synthetic",
  "is_synthetic": true,                    // NEVER dropped
  "status": "degraded",                    // ok | degraded | failed
  "warnings": ["upstream M21 resolved from sample; not live model output"],
  "upstream": [ { "model_id": "M21", "source": "sample" } ],
  "results": [
    {
      "entity_type": "zone",     // zone | gate | parking_site | route | asset ...
      "entity_id":  "Z01",       // which thing
      "kpi":        "expected_footfall",
      "timestamp":  "2027-08-02T06:15:00+05:30",
      "horizon_min": 15,         // how far ahead this row looks
      "state":      "forecast",  // current | forecast | scenario
      "value":      23766.8,
      "unit":       "persons/hr",
      "lower":      23457.6,     // uncertainty band...
      "upper":      25161.0,
      "quantile_level": 0.8,     // ...meaning an 80% band
      "risk_level": "red",       // green | amber | red | critical
      "reason_codes": ["SURGE"], // mandatory from amber upwards
      "recommendation": null,    // or an action needing approval
      "details": { "backend": "chronos2", "band_calibrated": true }
    }
  ]
}

The rules that make it trustworthy

  • A coloured warning must explain itself. Any record at amber or worse must carry a reason code. The contract rejects one that does not.
  • No self-executing actions. Every recommendation has requires_approval: true, enforced by the type system.
  • Bands mean what they say. quantile_level: 0.8 means the truth should land inside that band about 80 % of the time — and we measure whether it actually does (see calibration).
  • Degrade, never vanish. If an upstream model is missing or a library will not load, the service still answers and says what it fell back to.

The four endpoints

EndpointWhat it does
GET /healthIs the service alive?
GET /metadataWhat does this model do, what KPIs, what limitations?
POST /predictThe normal forecast
POST /scenarioA what-if — same shape, plus a comparison to baseline

5. The technology, in plain words

Worth correcting a common assumption: most of these are not machine learning models. Of the 25, nine use a forecasting foundation model, exactly one is a classic trained classifier, and fifteen are deterministic — formulas, rules, graph algorithms, optimisation and simulation. That is a deliberate choice: an operator has to be able to argue with a recommendation before approving it.
FamilyModelsWhat it actually is
forecast9 Chronos-2, a transformer foundation model for time series — like a language model, but for numbers. Used zero-shot: never trained on our data. Falls back to LightGBM (gradient-boosted decision trees) then a naive seasonal baseline.
rules4 Threshold and weighted-score logic. No learning: "if density > X for Y minutes and it is raining, risk = red". Every number lives in a YAML file.
network3 Graph algorithms on the real OpenStreetMap road graph — shortest paths, plus the BPR volume-delay function, a standard traffic-engineering formula.
vision2 RF-DETR (transformer object detector) + ByteTrack (tracking) + LWCC (crowd-counting CNN). Pretrained, used as-is. Plus optical flow.
formula2 Published equations. M21 uses the NOAA/NWS heat index — a polynomial from a meteorology paper. M07 will use a Poisson/Negative-Binomial GLM.
optimize2 Mixed-integer linear programming (PuLP / OR-Tools). Operations research: "minimise cost subject to these constraints".
location1 MCLP / LSCP facility-location models — "where do I put ambulances to cover the most people".
pedsim1 JuPedSim: simulates individual pedestrians walking and colliding. Physics.
mlclf1 The only conventional supervised model — a LightGBM classifier trained on the real AI4I 2020 machine-failure dataset.

Two things worth understanding about the forecasts

The naive baseline exists to be beaten

NaiveSeasonal is the dumbest forecast that is not random: "whatever happened exactly one day ago will happen again." No learning, no training, 30 milliseconds. Its entire job is to be the floor. If a transformer cannot beat "just copy yesterday", the transformer is adding nothing. It turns "our error is 190" — a number that means nothing alone — into "we are 43 % better than copying yesterday."

Backend on M01Error (MAE)vs naive
Chronos-2 (zero-shot)190.443 % better
LightGBM (fitted)223.233 % better
NaiveSeasonal335.3— the floor

The uncertainty bands had to be fixed

A band labelled "80 %" originally held the truth about half the time. The reason showed up immediately once measured per step: across a 3-hour horizon the error grows 26× while the raw band widens only 1.7×.

Horizon step14812
Typical error1769243455
Band width7691104132
Coverage86 %86 %43 %57 %

Every forecasting model now runs a conformal calibration at startup: it forecasts two dozen held-out moments from the past, measures how often the truth actually fell outside the band at each step, and widens each step to match. Coverage went from ~50 % to 74–90 %. Each record carries details.band_calibrated so you can tell.

6. How to run things

One-time setup

cd event-twin-claude-kit
uv venv --python 3.11
uv pip install -e "00_common[dev,geo,network,forecast,formula,mlclf,opt,vision,pedsim]"

Everyday commands

What you wantCommand
Run every testuv run pytest -q
Test one modeluv run pytest M05_parking_demand/tests -q
Check the whole repouv run python scripts/validate_all.py
Rebuild the worlduv run python -m twin_common.synthetic.generate --scenario S01
Tidy the codeuv run ruff check . --fix && uv run ruff format .

Running a model as a web service

uv run uvicorn api:app --app-dir M05_parking_demand --port 8005

Then ask it something:

# the default forecast — no body needed
curl -X POST localhost:8005/predict -H 'content-type: application/json' -d '{}'

# narrow it down
curl -X POST localhost:8005/predict -H 'content-type: application/json' -d '{
  "as_of": "2027-08-02T06:00:00+05:30",
  "horizon_min": 180,
  "entity_ids": ["P1", "P2"],
  "kpis": ["parking_occupancy"]
}'

# a what-if, with the difference against normal
curl -X POST localhost:8005/scenario -H 'content-type: application/json' -d '{
  "scenario_id": "S02",
  "compare_to_baseline": true
}'

Running one without a server

cd M05_parking_demand
uv run python -m src.run --out outputs/                 # writes sample_output.json
uv run python -m src.run --scenario S02 --out outputs/
The four inputs every model accepts. All are optional — send {} and you get a sensible default.
FieldMeaning
as_ofthe moment to answer for; defaults to the demo instant
horizon_minhow far ahead to look, in minutes
entity_idsonly these zones / gates / sites
kpisonly these measures
First start takes 10–25 seconds. The model loads a month of history, fits the forecaster once and calibrates its bands. That is startup cost, not per-request cost — requests afterwards take well under 2 seconds.

7. The models, one by one

Click any model to expand. 10 of 25 are built. Every one below is finished, tested and has a full model card in its folder.

M21 Weather Impact port 8021 · formula

Question it answers: what is the weather now and over the next few hours, and how does it change risk everywhere else?

This one was built first because almost everything else depends on it, and because it needs no upstream model at all. It is a formula model — no learning, no training.

What it gives you

temperatureheat_index rainfall_intensitywaterlogging_probability plus three multipliers other models read.

How it works

  • Heat index — the NOAA/NWS Rothfusz regression, the same polynomial the US weather service uses. Verified against 15 cells of the published NWS chart.
  • Waterlogging — a logistic curve in rainfall against each zone's own drainage capacity, plus a bonus for low-lying zones.

Try it

curl -X POST localhost:8021/predict -H 'content-type: application/json' -d '{}'
# 182 records: 9 entities (EVENT + 8 zones) x 3 hours

Scenarios: S01 normal · S03 heavy rain · S04 extreme heat

Honest limit: the "forecast" is a replay of stored weather, not a prediction. The docs allow this for the demo, but a real deployment needs a real weather API.
M01 Footfall Forecast port 8001 · forecast

Question it answers: how many people will arrive, by zone, by gate, over time?

This is the keystone. Thirteen of the other 24 models read it. If M01 is wrong, most of the twin is wrong.

What it gives you

expected_footfallpeak_footfall

156 records — 12 entities (8 zones Z01–Z08 + 4 gates G01–G04) × 12 fifteen-minute steps.

How it works

Chronos-2 forecasts all 12 series at once. It is told things it genuinely knows in advance — hour of day, day of week, whether it is a bathing day, temperature and rain — which is what makes a zero-shot forecast useful here.

Try it

curl -X POST localhost:8001/predict -H 'content-type: application/json' -d '{
  "entity_ids": ["Z01"], "kpis": ["peak_footfall"]
}'

Upstream: M21  ·  Scenarios: S01 · S02 more crowd · S03 rain · S05 gate closure

Honest limit: M01 declares itself insensitive to S04 (extreme heat) even though the spec lists it — nothing M01 reads responds to heat, and returning an unchanged answer while implying sensitivity would be worse than saying so.
M05 Parking Demand port 8005 · forecast

Question it answers: how full will each car park get, and when does it overflow?

What it gives you

parking_demandparking_occupancy parking_search_time — 108 records for 3 sites (P1, P2, P3).

Occupancy can go above 100 %. That is deliberate. The stored data caps "occupied" at the number of bays, so a model trained on it could never predict an overflow — the one thing this model exists to warn about. M05 forecasts demand instead. 130 % means 30 % of arriving drivers have nowhere to go. details.occupied_spaces has the capped figure.

Try it

curl -X POST localhost:8005/predict -H 'content-type: application/json' -d '{}'
# at the demo instant P1 reads ~123% — overflowing, with a shuttle diversion recommended

Upstream: M01  ·  Scenarios: S01 · S02

M06 Transit / Shuttle Demand port 8006 · forecast

Question it answers: how many passengers and how many shuttle vehicles does each route need?

The first model with two upstreams (M01 and M05) — the first real test of the dependency chain.

What it gives you

shuttle_demandshuttle_requirement passenger_wait_time — 72 records for 2 routes (SH1, SH2).

Finding: the fleet is far too small. The routes need 369 vehicles on an ordinary day and 1,447 at the peak, against a configured fleet of 80 — 18× short. This was deliberately not "fixed", because fleet size belongs to M24 (not built yet). M06 reports the true requirement and recommends the shortfall. The gap is the finding.

Scenarios: S01 · S02  ·  insensitive to S06/S12 (needs M04)

M15 Water Demand port 8015 · forecast

Question it answers: how much water does each zone need, is there a shortfall, and how many water points and tankers?

What it gives you

expected_water_demandwater_supply_demand_gap drinking_water_point_requirementwater_tanker_requirement — 296 records across 8 zones.

A positive gap means a shortage. A surplus is reported as a negative number rather than hidden, because "how much spare have we got" is a real question.

Try it

curl -X POST localhost:8015/scenario -H 'content-type: application/json' -d '{
  "scenario_id": "S08"   // power cut: a pump stops, the gap widens, tankers called
}'

Upstream: M01, M21  ·  Scenarios: S01 · S02 · S04 heat · S08 power failure

Honest limit: the heat effect (S04) is real but small and short-lived — 0.1 % at 06:00 (a cool morning), 8.5 % at midday — and it decays across the horizon, so treat it as a one-hour signal. Leakage is not modelled at all.
M17 Food & Supply port 8017 · forecast

Question it answers: how much food is needed, how long does stock last, how many deliveries?

The decision is whether to place an order now, which drives every design choice.

What it gives you

food_demandfood_stock_coverage delivery_requirement — 72 records for 2 outlets.

Two things are different here. The data is hourly, not 15-minute. And the default horizon is 12 hours, deliberately longer than the 6-hour supplier lead time — inside a window shorter than the lead time, nothing you order can arrive, so a supply disruption would show no effect at all.

Stock is simulated forward: an order placed now arrives lead_time hours later, and if that falls outside the window the shelf keeps draining. Under a supply disruption (S13) coverage falls to 0.88× and stockout warnings double.

Upstream: M01  ·  Scenarios: S01 · S02 · S13

M18 Waste Generation port 8018 · forecast

Question it answers: how much waste, when do bins overflow, how many collection trips?

What it gives you

waste_generationwaste_bin_fill_level waste_collection_tripsbin_overflow_time — 296 records across 8 bin groups.

Fill is projected forward from the last reading and reset when the collection round arrives. bin_overflow_time says how many minutes until a group is full; a bin that is not going to overflow reports 999 rather than 0, so "fine" cannot be misread as "overflowing now".

A bug worth knowing about. bin_capacity_kg is one bin (120 kg), but each WB01–WB08 is a whole zone's group of bins. The generator was dividing a zone's waste by a single bin, so every group read 100 % full within one step — both fill KPIs carried no information at all. Adding bins_per_group: 50 fixed it; the busiest group now peaks at 97 % instead of being pinned at 100 %.

Upstream: M01  ·  Scenarios: S01 · S02

M19 Power Load port 8019 · forecast

Question it answers: what electrical load is expected, and how long can backup generators last?

What it gives you

electricity_demandgenerator_backup_duration backup_generator_requirement — 72 records for 2 substations.

Reported in MW; the kW figure is kept in details. It also publishes details.load_utilization specifically for M12 (fire risk) to consume later.

Try it

curl -X POST localhost:8019/scenario -H 'content-type: application/json' -d '{
  "scenario_id": "S08"   // SS01 fails: on backup, countdown starts
}'
Two bugs this model exposed. First, the data has one row per (substation, zone) pair — splitting on substation alone silently reported a quarter of the real load, with no error anywhere. Second, generators never refuelled, so after a month of daily outages the tank was empty and the backup countdown read zero for the one scenario the KPI exists for. Both fixed.

Upstream: M01, M21  ·  Scenarios: S01 · S02 · S04 · S08

M20 Network Capacity port 8020 · forecast

Question it answers: will communications — CCTV backhaul and command links — overload or fail?

Everything in the control room depends on this. The KPIs separate congestion from availability, because a tower can be perfectly uncongested and still be off.

What it gives you

bandwidth_utilizationnetwork_availability network_capacity_risk — 324 records for 3 towers. Data is on a 5-minute grid here.

Finding: this world never runs out of bandwidth. Peak utilisation is 27.5 %, so the capacity-risk KPI sits near zero. That is the correct answer for these tower capacities — and the threshold was deliberately left where an operator would want it rather than lowered to make the number look exciting. The real constraint here is power-driven availability, not congestion.

Upstream: M01  ·  Scenarios: S01 · S02 · S08 power · S09 CCTV failure

M22 Environmental Risk port 8022 · forecast

Question it answers: where will air quality or noise get worse, and what are the emissions?

This model uses the one genuinely REAL table in the project — cached Open-Meteo air-quality history. Its rows carry is_synthetic: false.

What it gives you

pm25air_quality_index noise_levelco2_emissions — 66 records.

  • AQI — the Indian National AQI: a sub-index per pollutant, and the AQI is the worst of them, not the average. Averaging would let a clean pollutant mask a dangerous one.
  • Noise — logarithmic in crowd density, which is why 30 % more crowd is only about 1 % more decibels.
Do not publish numbers from this model yet. The AQI breakpoints are transcription placeholders and need checking against the official CPCB table; all three CO₂ emission factors are placeholders; and the CO₂ traffic term is zero because M04 does not exist yet — every record says so in details.traffic_term.

8. Scenarios — the what-if machine

A scenario is a named change to the world. You ask any model the same question under that change, and it answers in the identical shape with state: "scenario".

A model that cannot respond says so. Ask M01 about extreme heat and it returns the baseline with status: degraded and a warning "insensitive to S04" — rather than returning unchanged numbers and letting you believe it considered the heat. That honesty is enforced by tests in every model.

10. Glossary

KPIOne measured quantity, e.g. parking_occupancy. There are 109 defined across the project.
ZoneA named area: Z01–Z08 (ghats, corridors, market, transit hub).
Snan dayThe peak ritual bathing day — the busiest day of the event.
HorizonHow far ahead an answer looks, in minutes.
UpstreamA model whose output another model reads.
DegradedThe service answered, but something was missing — and it says what.
Zero-shotA model used without training it on our data.
CovariateSomething known in advance that helps a forecast — the hour, the weather, whether it is a bathing day.
Conformal calibrationMeasuring how often a band was actually right, and widening it until it is.
Common random numbersGiving every scenario the same random noise so comparisons measure the change, not luck.
