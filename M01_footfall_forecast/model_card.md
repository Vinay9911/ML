# Model card — M01 Footfall Forecast

## Question / decision supported
How many people will arrive, by zone, gate and time?

M01 is the busiest node in the dependency graph. **M03, M04, M05, M06, M07, M11, M15, M16,
M17, M18, M19, M20 and M24 all read it.** An error here propagates to most of the twin, which
is why it carries the full three-backend comparison below rather than a single number.

## Method
| Aspect | Detail |
|---|---|
| Engine | `twin_common.engines.forecast` |
| Default backend | Darts `Chronos2Model`, zero-shot, `autogluon/chronos-2-small` (28M) |
| Fallbacks | Darts `LightGBMModel` (quantile regression) → `NaiveSeasonal(K=96)` |
| Series | 12: one per zone (Z01–Z08) and one per gate (G01–G04) |
| Covariates (future) | hour-of-day sin/cos, day of week, `is_snan_day`, `temperature_c`, `rain_mm` |
| Quantiles | 0.1 / 0.5 / 0.9 → `lower` / `value` / `upper`, `quantile_level: 0.8` |
| Grid | 15 minutes; default horizon 180 min (12 steps) |
| Libraries | darts 0.47.0 (Apache-2.0), lightgbm 4.7.0 (MIT), torch 2.14.0+cpu (BSD) |

**Why Chronos-2 and not TimesFM.** docs/06 §3: `Chronos2Model` supports past and future
covariates; `TimesFM2p5Model` does not. The covariates are the whole reason this forecast is
interesting, so a backend that cannot take them is not useful here.

**No fine-tuning.** docs/06 §3 forbids fine-tuning a foundation model on synthetic data, and
none is done. Darts still requires `fit()` before `predict()`, but with no
`enable_finetuning` it only registers the series (0.7 s after the weights are cached).

**Warm start.** The engine fits once in `load()` and caches the fitted model. Without that,
every request paid the fit — measured 8.9 s against a 10 s budget (docs/02 §6).

## Inputs and features
| Source | Detail |
|---|---|
| Tables | `footfall_15min` (D01), `gate_entries`, `event_calendar` (D21), `weather_hourly` (D12), `zones` (D03) |
| Upstream | M21 — the rain and heat multipliers, reported in `details.weather` |
| History | 28 days of 15-minute context, capped at 2,688 steps (four weeks) |

## Assumptions
Every value is a **placeholder** and lives in `config.yaml`, never in the code.

| Config key | Value | Meaning |
|---|---|---|
| `params.forecast.backend` | `chronos2` | which backend to try first |
| `params.forecast.hub_model_name` | `autogluon/chronos-2-small` | the CPU-sized model |
| `params.forecast.quantiles` | `[0.1, 0.5, 0.9]` | the 80% band |
| `params.forecast.input_chunk_length` | 96 | one day of context |
| `params.forecast.max_context_steps` | 2688 | four weeks of history |
| `params.steps_per_hour` | 4 | 15-min counts → persons/hr |
| `params.confidence` | 0.6 | heuristic, not calibrated |
| `params.backtest.folds` | 7 | rolling origins over the last 7 days |

## Evaluation

> These metrics are computed on **synthetic** data. They measure **pipeline correctness**,
> not real-world accuracy. Nothing here is evidence that M01 would forecast a real crowd
> this well.

Rolling-origin backtest, entity Z01, horizon 12 steps (180 min), 7 folds, CPU:

| Backend | MAE | MAPE | Pinball (q0.5) | 80% coverage | Time |
|---|---:|---:|---:|---:|---:|
| **chronos2** (zero-shot) | **194.7** | **24.0%** | **97.33** | 61.9% | 1.8 s |
| lightgbm (fitted) | 205.5 | 27.9% | 102.76 | 39.3% | 14.3 s |
| naive (K=96) | 309.5 | 58.4% | 154.77 | — | 0.1 s |

Source: `data/derived/backtest.json`, regenerated by `Model.backtest()`.

**What this shows.**
- Both learned backends comfortably beat the naive seasonal floor (MAE 309.5), so the
  forecast is doing real work rather than repeating yesterday.
- Zero-shot Chronos-2 slightly beats a LightGBM **fitted on this very history**, and is
  8× faster. That is a striking result, and it should be treated with suspicion rather than
  celebrated: the synthetic world has a clean, strongly periodic structure that suits a
  foundation model's priors. It says little about a real crowd.
- **This is not a like-for-like comparison.** Chronos-2 never sees the training data;
  LightGBM is fitted on it. docs/06 forbids fine-tuning, so a fair contest is not available
  here.

**Interval coverage is the weak result.** Both backends fall well short of the nominal 80%
(61.9% and 39.3%), meaning the bands are **too narrow** — the model is more confident than it
should be. A downstream consumer that treats `lower`/`upper` as a genuine 80% interval will
be over-confident. Widening the quantiles or calibrating the bands is the first thing to fix
with real data.

## Limitations and failure modes
- **Synthetic context.** A foundation model has never seen this world, and the world is
  generated from placeholder assumptions. The backtest measures the pipeline.
- **Bands are under-dispersed.** See coverage above. `confidence: 0.6` is a fixed heuristic,
  not a calibrated probability.
- **Covariates are known exactly.** Temperature and rain are read from the generated world.
  With a real feed they would themselves be forecasts carrying their own error, and accuracy
  would fall.
- **S04 is not supported, despite the docs/03 M01 card listing it.** The docs/03 M21 arrival
  multiplier is a function of rain only, so extreme heat changes nothing M01 reads. Rather
  than return an unchanged baseline while implying sensitivity, M01 declares itself
  insensitive and returns the documented degraded response (docs/05 §1.2). Add a heat term
  to the M21 arrival multiplier to change this.
- **Scenarios without a generated world** fall back to scaling the S01 history through the
  generic adjustment layer, and the response says so in a warning. That is cruder than
  regenerating the world for that scenario.
- **Gate closure is applied as a zero**, not re-simulated. The redistribution to other gates
  comes from the generated S05 world when it exists; otherwise the other gates are unchanged.

## Real-data readiness
| Step | What is needed |
|---|---|
| Data | gate counter or CCTV aggregates in the D01 schema; real weather in D12 |
| Recalibration | the quantile levels, after measuring actual interval coverage |
| Retraining | optional: Darts `enable_finetuning` once several weeks of real history exist (docs/06 §3 forbids it on synthetic data) |
| Re-backtest | rerun `Model.backtest()`; the table above must be replaced before anyone relies on it |
| New capability | forecast uncertainty on the covariates themselves |
